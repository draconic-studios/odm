# Progen engine and Obsidian contract

## Question

Which store engine do we wire day one, and what does “Obsidian vault compatible” mean for ODM Progens?

## Blocked by

_(none)_

## Answer

**Engine:** Implement store ops in-repo in `odm-progen` (Markdown walk + disposable SQLite FTS). Do **not** require a path dependency on external progenitor crates for phase 3. Keep the façade API thin so a later ticket can swap internals to upstream `progen-ops` without changing CLI contracts.

**Obsidian / obsidian-cli contract:**

1. A Progen `path` **is** a vault root — openable as an Obsidian vault and usable with obsidian-cli against that folder.
2. **Files are authoritative:** plain `.md` with optional YAML frontmatter; body may contain `[[wikilink]]` / `[[target|alias]]` (Obsidian-style). No proprietary binary content format.
3. **Index is disposable and ODM-owned:** only under `.odm/progen/<name>/` (gitignored). Never require an engine database inside the vault for ODM to function.
4. **Coexistence:** if `.obsidian/` already exists, leave it alone. On local `progen add` (no clone), scaffold a minimal vault (`README.md` + minimal `.obsidian/app.json`) so Obsidian recognizes the folder.
5. **Identity for ODM ops:** prefer frontmatter `id` when present; else stable path-relative stem. Federated identity remains `(progen, id)` per `progen.md`.
6. **Non-goals here:** full Obsidian plugin API, sync services, or requiring Obsidian installed to run ODM.
