# Shared fsutil tree copy and pack dest prep

## Description

Generate and agent pack each own tree-copy, symlink handling, and force/overwrite policy. Pack install vs link dest preparation is nested match density. Behavior is already tested per feature; structure should share the FS engine without changing generate dry-run, force type-conflict, or pack install/link/rm semantics.

## Affected

- odm-core generate and agent_pack modules
- Unit tests for generate force/dry-run and pack install/link dest cases

## Impact

Duplicated Code; force/overwrite edge cases will drift; agent_pack stays oversized.

## Proposed Fix

See Agent Brief.

## Blocked by

None

## Agent Brief

> *This was generated by AI during triage.*

**Category:** refactor  
**Summary:** Extract a shared filesystem helper used by local generate materialize and agent pack install/link copy paths; collapse pack dest prep without product behavior change.

**Current behavior:**

- Generate walks a template tree: count for dry-run, copy files/dirs/symlinks, and on force removes type conflicts (file↔dir) before write.
- Agent pack has a parallel copy_tree and separate prepare_dest paths for install vs link with force/empty-dir/symlink/file branching.
- Semantics differ at the policy edge (pack registry, link vs copy, generate dest under workspace) but the FS primitives rhyme.

**Desired behavior:**

- One internal fsutil (or `io` sibling) provides shared primitives: copy tree, count tree, remove path, detect empty dir, copy/create symlink, and optional “remove type conflict then write” used by generate force.
- Generate and agent_pack become thin policy over those primitives (dest roots, force flags, link vs directory install).
- Pack install and link dest preparation share one skeleton: ensure parent → lexists branch → force or empty-dir special cases → terminal action (mkdir tree / symlink). Prefer a table/clear match over nested else-if ladders.
- Dry-run generate still performs no writes and reports the same counts.
- Pack install/link/rm and generate `--force` type-conflict behavior remain as locked by existing tests and docs.
- No public CLI flag or JSON shape changes.

**Key interfaces:**

- Generate local materialize + dry-run entrypoints — signatures stable
- Pack install/link/rm entrypoints — signatures stable
- Error kinds (usage / operation / not_found) for existing failure modes — stable

**Acceptance criteria:**

- [ ] A single shared tree-copy (and count if separate) implementation serves both generate and pack copy paths
- [ ] Pack install and link dest prep no longer maintain two fully independent nested ladders for the same exists×force policy
- [ ] All existing generate dry-run/force and pack install/link/rm unit + integration tests pass without relaxing assertions
- [ ] Touched files ≤1000 LOC preferred, ≤1250 hard
- [ ] `cargo test` green; `cargo clippy --workspace --all-targets -- -D warnings` clean

**Out of scope:**

- Remote generate / marketplace packs
- Changing force defaults or dest layout conventions
- Inventory or CLI spine work
- New public fsutil crate export for external users (internal module is enough)
